# Go 开发规范

这是上游 `golang-patterns` 的精简适配版，不是逐字镜像。来源与改动见 [技能说明](../README.md)，上游许可证见 [LICENSE](LICENSE)。

根据当前请求或 `$ARGUMENTS` 应用相关规则；不要为了符合模板而重构无关代码。涉及 Discord 行为时，同时参考项目的 `discord-go` skill。

## 开始前

- 阅读适用的项目约定、`go.mod`、`go.work`（如有）及已有测试、构建配置，沿用现有风格。
- 以项目声明的 Go 版本和锁定的依赖版本为准；不要直接复制网上的旧工具链或 linter 配置。
- 没有 Go 模块时，只在任务要求创建应用时初始化；不要为执行检查而生成占位模块，也不要猜测用户的远程仓库地址。
- 修改 SDK 用法前核对对应版本的官方文档或源码。可用时先查 Context7，再用本地 `go doc`、源码和编译结果确认签名。

## 结构与接口

- 采用最小可用结构；按业务职责拆包，不预先生成没有用途的分层、接口或 `pkg/` 目录。
- 入口负责配置加载、依赖组装和生命周期；事件处理器负责输入与输出，业务规则保持可独立测试。
- 包名简短、小写，导出标识符有必要的注释；匹配项目现有注释密度。
- 在消费方定义小接口，只抽象实际需要替换或隔离测试的依赖。通常返回具体类型，但不要把它当作绝对规则。
- 优先标准库和已有依赖；避免全局可变状态、隐藏的 `init()` 副作用和过度使用函数选项。

## 错误与资源

- 先处理错误，成功路径少缩进；需要保留错误链时使用 `fmt.Errorf("操作说明: %w", err)`。
- 使用 `errors.Is` / `errors.As` 分类错误，不依赖错误字符串匹配。
- 在合适的边界记录错误，避免逐层重复打印；给用户的错误信息不包含凭据、内部 SQL 或敏感上下文。
- 不用 `panic` 处理可预期的业务失败，不用空标识符随意丢弃错误。忽略最佳努力清理错误时说明原因。
- 成功取得资源后安排关闭；处理必要的关闭或刷新错误。设置网络超时，并限制不可信响应体的读取大小。
- 池化对象归还后不再读写，也不返回其底层切片；需要返回数据时先复制。只有测量证明有收益才引入 `sync.Pool`。

## 并发与取消

- 请求相关函数通常以 `context.Context` 为首个参数；调用链传递取消与截止时间，不用新的 `context.Background()` 丢弃上游取消。
- 每个 goroutine 都有明确的退出路径和所有者；可能阻塞的发送、接收与 I/O 要能结束。
- 由发送侧的明确所有者关闭 channel；接收方不要关闭仍可能被发送的 channel。返回结果 channel 的函数应约定错误、取消和结束的表达方式。
- 用互斥锁、channel 或适当的原子操作保护共享状态；不要并发读写普通 map。
- 按需使用有界队列、worker pool 或 `errgroup`；不要为每个外部事件无限制启动长期任务，也不要引入依赖只为替代简单的 `sync.WaitGroup`。
- 按 `go.mod` 中的语言版本判断循环变量语义；Go 1.22+ 不需要机械地为每个循环添加旧式变量捕获补丁。
- 退出时停止接收新工作、取消任务、等待必要的清理，并给清理阶段设置独立且有限的超时。

## 数据与性能

- SQL 使用参数绑定和带 context 的接口；原子业务变更用事务或合适的原子 SQL，不用应用层先读后写代替并发控制。
- 明确连接池、缓存和队列的容量及生命周期；默认不引入分布式基础设施。
- 已知规模时合理预分配切片，字符串拼接优先现有标准库方法；不以牺牲可读性换取未经测量的微优化。
- 数据库驱动、cgo 和目标平台会影响编译及部署方式；不要一概承诺完全静态的二进制。

## 验证与交付

只在存在相应 Go 源码、模块和工具链时执行项目已有检查。先格式化本次改动的 Go 文件，再按任务运行：

```sh
go vet ./...
go test ./...
go test -race ./...
go build ./...
```

- 竞态检测依赖受支持的平台及工具链；无法执行时报告原因，不能写成通过。
- 第三方 linter 沿用项目已有版本与配置，不自动全局安装；`go mod tidy` 只在需要依赖整理时执行，并检查差异。
- 测试应默认离线；真实外部服务访问需另行明确授权。
- 交付时列出实际改动、实际运行的检查及失败或跳过项。仅修改文档时不要声称 Go 应用已编译或运行。
